# PickMe — архитектура MVP

## Работа с Git

Рабочая ветка проекта — `dev`. Каждое самостоятельное изменение оформляй отдельным коммитом в `dev`.

## Пользовательский сценарий

1. Посетитель открывает главную страницу со списком животных и может перейти в карточку любого животного.
2. Пользователь регистрируется по email и паролю, затем входит через отдельную страницу. После входа он возвращается в каталог.
3. Вошедший пользователь открывает форму добавления и указывает кличку, место обнаружения и породу. При желании он прикладывает одну фотографию. После сохранения открывается новая карточка, а животное появляется в начале каталога.
4. Выход завершает текущую сессию и возвращает пользователя в каталог.

Для MVP принимаем, что каталог, карточки и фотографии доступны гостям. Каждый зарегистрированный пользователь может добавлять животных после входа. Все пользователи работают с общим каталогом.

## Устройство приложения

Go отвечает за HTTP API на `net/http`, проверку данных, сессии и работу с PostgreSQL. Фронтенд — отдельный набор HTML/CSS/JS. JavaScript вызывает API через `fetch`, выводит полученные данные на страницу, обрабатывает ошибки и выполняет переходы после отправки форм.

В Docker Compose Nginx отдаёт файлы фронтенда и проксирует `/api/` в Go. Браузер загружает страницу и обращается к API по одному адресу, поэтому отправляет cookie сессии с запросами на относительные пути `/api/...`. Например, на странице `/` JavaScript вызывает `GET /api/animals` и строит карточки из JSON.

Запросы к PostgreSQL находятся в пакетах `auth` и `animals`. Оба используют общий пул `pgxpool` и параметризованный SQL. `cmd/pickme` собирает зависимости и запускает API. Go-модуль — `github.com/bypara/PickMe`. Сервер использует поддерживаемую версию Go с `http.CrossOriginProtection`.

```text
cmd/pickme/              точка входа, запуск и остановка API
internal/config/         настройки из окружения
internal/httpserver/     маршрутизация API, middleware и HTTP-ответы
internal/auth/           регистрация, вход, выход и проверка сессий
internal/animals/        каталог, карточки, добавление животных и фото
web/                     отдельный фронтенд на HTML/CSS/JS
  pages/                 страницы каталога, карточки, добавления, входа и регистрации
  static/                CSS, JS (включая общий клиент API) и изображение-заглушка
  nginx.conf             выдача фронтенда и проксирование /api/
  Dockerfile             образ Nginx с файлами фронтенда
migrations/              версионируемые SQL-миграции Goose
Dockerfile               сборка Go API и инструмента миграций
compose.yaml             сервисы web, app, db и migrate
.env.example             пример локальных настроек
```

## Модель данных

| Таблица | Поля и ограничения |
| --- | --- |
| `users` | `id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY`, `email text UNIQUE NOT NULL`, `password_hash text NOT NULL`, `created_at timestamptz NOT NULL DEFAULT now()`. В `email` сохраняется значение после удаления внешних пробелов и приведения к нижнему регистру. |
| `sessions` | `token_hash bytea PRIMARY KEY`, `user_id bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE`, `expires_at timestamptz NOT NULL`. Индекс по `expires_at` для удаления истёкших сессий. |
| `animals` | `id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY`, `name text NOT NULL`, `found_location text NOT NULL`, `breed text NOT NULL`, `created_by bigint NOT NULL REFERENCES users(id)`, `created_at timestamptz NOT NULL DEFAULT now()`. Индекс по `(created_at DESC, id DESC)` для каталога. |
| `animal_photos` | `animal_id bigint PRIMARY KEY REFERENCES animals(id) ON DELETE CASCADE`, `content_type text NOT NULL`, `data bytea NOT NULL`. Ограничения `CHECK` допускают `image/jpeg` и `image/png`, а также размер от 1 байта до 5 МиБ. |

Кличка и порода занимают от 1 до 100 символов, место обнаружения — от 1 до 255 после удаления внешних пробелов. Эти ограничения действуют в серверной валидации и в БД. `created_by` берётся из проверенной сессии. Каталог показывает сначала новые записи по `created_at DESC, id DESC`. Каталог и карточка выбирают текстовые поля и признак наличия фото. Байты читаются отдельным запросом при открытии фотографии.

## Страницы фронтенда

| URL | Поведение фронтенда |
| --- | --- |
| `/` | Загружает `GET /api/animals` и показывает карточки или пустой каталог. |
| `/register` | Отправляет `POST /api/register`. После успешной регистрации открывает `/login`. |
| `/login` | Отправляет `POST /api/login`. После успешного входа открывает `/`. |
| `/animals/new` | Проверяет сессию через `GET /api/me`, отправляет `POST /api/animals` и открывает карточку из ответа. Гостя и пользователя с истёкшей сессией направляет на `/login`. |
| `/animals/{id}` | Берёт `id` из URL, загружает `GET /api/animals/{id}` и заполняет карточку. |

Фронтенд использует `GET /api/me`, чтобы показать пункты навигации для гостя или пользователя с сессией. Пользователь с действующей сессией со страниц входа и регистрации возвращается на `/`. Кнопка выхода отправляет `POST /api/logout` и после подтверждения открывает каталог. Проверка прав на запись выполняется в Go API при каждом запросе.

## Контракт API

| Метод и путь | Доступ | Успешный ответ |
| --- | --- | --- |
| `POST /api/register` | Гость | `201` и объект созданного пользователя. |
| `POST /api/login` | Гость | `200`, объект пользователя и `Set-Cookie` для новой сессии. |
| `POST /api/logout` | Все | `204` и `Set-Cookie` для удаления cookie. Повторный выход даёт тот же результат. |
| `GET /api/me` | Все | `200` и `{"user":null}` для гостя или объект пользователя в поле `user` для действующей сессии. |
| `GET /api/animals` | Все | `200` и JSON-массив животных в порядке каталога. |
| `POST /api/animals` | После входа | `201` и объект сохранённого животного. Заголовок `Location` указывает на `/api/animals/{id}`. |
| `GET /api/animals/{id}` | Все | `200` и объект животного. |
| `GET /api/animals/{id}/photo` | Все | `200` и байты JPEG или PNG. |

Объект пользователя содержит `id` и `email`. Объект животного содержит `id`, `name`, `found_location`, `breed`, `created_at` в RFC 3339 и `photo_url` со значением `/api/animals/{id}/photo` или `null`. Идентификаторы в JSON передаются строками, чтобы JavaScript сохранил точность PostgreSQL `bigint`. Пустой каталог возвращает `[]`.

Фронтенд отправляет `email` и `password` в JSON для регистрации и входа. Для добавления отправляет `FormData` с полями `name`, `found_location`, `breed` и необязательным файлом `photo`. Браузер формирует `Content-Type: multipart/form-data` вместе с границей частей.

Ошибка API содержит `{"error":{"code":"...","message":"..."}}`. Для ошибок валидации `422` объект `error` может содержать `fields` с сообщениями для полей. `400` означает некорректное тело запроса, `401` — неверные данные входа или отсутствие действующей сессии на защищённом маршруте, `403` — отказ проверки источника запроса, `404` — неизвестный или некорректный `id` либо отсутствующее фото, `409` — занятый email или попытка входа или регистрации с действующей сессией, `413` — превышение лимита загрузки. При сбое БД API логирует детали и возвращает `500` с общим сообщением. Фронтенд показывает ошибки в интерфейсе и обрабатывает сетевые сбои и ответы прокси без JSON.

## Аутентификация и сессии

- При регистрации сервер проверяет формат email и пароль длиной от 12 до 128 символов. Пароль хешируется Argon2id с индивидуальной случайной солью. В БД хранится кодированная строка с параметрами, солью и хешем. Уникальность email проверяет БД, в том числе при одновременной регистрации.
- При входе сервер сверяет хеш пароля. Для неизвестного email и неверного пароля используется одно сообщение «Неверный email или пароль».
- После успешного входа сервер генерирует случайный токен из 32 байт. Браузер получает его в cookie `pickme_session`, а PostgreSQL — SHA-256 этого токена. Срок действия сессии и cookie — 24 часа со входа. Атрибуты cookie — `HttpOnly`, `SameSite=Lax`, `Path=/api`. `Secure` включается при HTTPS через настройку окружения.
- Middleware сессии ищет хеш из cookie в БД и проверяет `expires_at`. При действующей сессии он помещает ID пользователя в контекст запроса. Ошибка БД передаётся в общую обработку ошибок. Защищённые маршруты оборачиваются `auth.RequireUser`. Go-обработчики используют `auth.CurrentUser(*http.Request) (int64, bool)`, а фронтенд узнаёт о сессии через `/api/me`. Ответы с данными сессии помечаются `Cache-Control: no-store`.
- Выход удаляет запись текущей сессии по хешу и отправляет cookie с истёкшим сроком. Запросы, меняющие данные, выполняются через `POST` и защищаются общим `http.CrossOriginProtection`.

## Добавление животного и загрузка фото

1. Middleware проверяет сессию перед чтением тела запроса. Сервер ограничивает всё тело формы до 6 МиБ через `http.MaxBytesReader` и отдельно проверяет лимит 5 МиБ на файл.
2. Сервер проверяет текстовые поля и содержимое файла. Принимаются JPEG и PNG. Перед полным декодированием проверяются размеры изображения, предел — 16 мегапикселей. MIME-тип определяется по содержимому, имя загруженного файла не используется. Временные файлы multipart-парсера удаляются после обработки запроса.
3. После проверки полей и фото сервер создаёт запись в `animals` и при наличии фото добавляет запись в `animal_photos` в одной транзакции. Если запись фото завершается ошибкой, транзакция откатывается целиком. API возвращает `201` после `COMMIT`, а фронтенд открывает карточку по `id` из JSON.
4. Изображение отдаётся по `/api/animals/{id}/photo` с сохранённым `Content-Type` и `X-Content-Type-Options: nosniff`. Фронтенд использует `photo_url` в `src` и показывает статичную заглушку при `photo_url: null`. Отдельная таблица позволяет хранить фото и карточки в одном постоянном томе PostgreSQL и сохранять их вместе.

## Docker Compose и миграции

- `db` запускает PostgreSQL с healthcheck через `pg_isready` и постоянным именованным томом. Сервис доступен приложению во внутренней сети Compose.
- `migrate` дожидается статуса `service_healthy` у `db`, применяет SQL-миграции через `goose up` и завершает работу. `app` стартует после `service_completed_successfully` у `migrate`.
- `app` запускает Go API на `:8080` во внутренней сети. Приложение получает `DATABASE_URL`, `HTTP_ADDR` и `COOKIE_SECURE` из окружения. Пример значений хранится в `.env.example`. Локальный `.env` добавляется в `.gitignore`.
- `web` запускает Nginx и публикует порт `8080` хоста. Он обслуживает страницы и `/static/`, направляет `/api/...` в `app:8080` с сохранением пути и исходного `Host`, допускает тело запроса до 6 МиБ. Локальный запуск проекта — `docker compose up --build`. Страницы доступны на `http://localhost:8080`, API — по `/api/` на том же адресе.
- Начальные миграции покрывают все четыре таблицы. Последующие изменения схемы оформляются новыми файлами. Версии образов и инструмента миграций фиксируются при реализации.

## Ответственность и порядок разработки

| Разработчик | Зона ответственности |
| --- | --- |
| №1 | Структура проекта, общий Go API, Docker Compose и Nginx, миграции всей БД, API регистрации, входа, выхода и проверки сессии. Общая навигация, клиент API, страницы входа и регистрации и подключение их к API. |
| №2 (Дима) | API каталога, карточки, добавления животного и выдачи фото. Валидация и хранение фото, запросы к `animals` и `animal_photos`, главная страница, карточки и форма добавления с запросами к API. |

1. Разработчик №1 подготавливает каркас с Compose, миграциями, статическим фронтендом, прокси и интерфейсом `RequireUser` / `CurrentUser`. Миграции животных готовы к этому этапу, чтобы Дима мог работать с реальной схемой.
2. После общего каркаса разработчики параллельно реализуют свои сценарии и коммитят самостоятельные изменения в `dev`. Дима подключает маршруты животных в коде своего пакета и использует согласованный middleware.
3. Когда обе части готовы, проверяются `go test ./...`, запуск Compose на чистой БД и сквозной сценарий в браузере. Повторный запуск проверяется с уже заполненным томом.

## Проверка готовности MVP

- Гость открывает каталог, карточку и фото. Страница добавления направляет гостя на вход. Прямой `POST /api/animals` без действующей сессии возвращает `401`.
- Регистрация создаёт аккаунт. Повторный email и неверный пароль дают сообщения об ошибке. После выхода прежняя cookie больше не даёт доступ к добавлению.
- Животное с фото и животное без фото появляются в каталоге. Невалидные поля, повреждённое изображение и превышение лимита оставляют БД без новой карточки.
- После перезапуска Compose аккаунты, карточки и фото доступны. Миграции на уже заполненной БД повторно стартуют без ошибок.
